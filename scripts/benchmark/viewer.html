How the comparison works

One test at a time on the selected container. Its current memory cap, CPU allowance, worker count and upstream concurrency are captured and preserved for every run. Each workload begins with empty rendered-tile and vector caches and fresh workers. Fonts, sprites and shaders remain. Background work drains before the next run. Original server settings are restored afterwards.

Synthetic: six batches of 24 fresh requests; eight 12-request jumps, 1.5 seconds apart, abandoning the previous view; repeat the last view from cache; then a 6×4 tile view moving two columns east after delivery, with a 350 ms pause.

Human / fixed timing: request coordinates and intervals from the trimmed recording, including recorded client cancellations. Every configuration faces the same arrival schedule. Requests originally answered 304 are replayed as full requests, so every run begins comparably cold.

Human / tile-driven: the same request bursts, waiting for each burst to finish before a 300 ms pause. This is a responsiveness model, not a reconstruction of your gestures. Bursts split at a 350 ms quiet gap or a profile/zoom change. Browser-cached tiles and exact viewport movements were not recorded.

Human / partial delivery: preserves timing within each request burst. After dispatching that burst, it waits at least 100 ms, then moves when 75% has arrived or after 1.5 seconds. Unfinished requests can overlap the next burst; recorded abandonment timers are retained. This is an explicit sensitivity model, not exact camera movement. Route time ends when it moves on from the final burst; remaining responses are measured separately.

Fairness: compare foreground completion and response distributions, not just how much background work was discarded. Results from different replay modes stay separate. The read-only viewer adds no tile requests.
